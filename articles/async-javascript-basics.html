Async JavaScript Basics

Callbacks, timers, and why asynchronous JavaScript can become difficult to reason about.

When I first encountered asynchronous JavaScript, the syntax itself wasn't particularly difficult. 

setTimeout(() => {
  console.log("Hello");
}, 2000);

What was confusing was what JavaScript was actually doing with that function.

Does JavaScript stop for two seconds? Is the function running in the background? And what exactly is a callback?

The important thing is to understand the mental model, not just memorize the syntax.

First: Synchronous vs Asynchronous

Consider ordinary JavaScript: 

console.log("A");
console.log("B");
console.log("C");

The code executes in order: 

A → B → C

Each statement runs before the next one.

But now consider: 

console.log("A");

setTimeout(() => {
  console.log("B");
}, 2000);

console.log("C");

The output is: 

A
C
B

Why?

Because setTimeout() schedules the callback to run later. It does not stop the rest of the JavaScript from executing.

What is a Callback?

A callback is simply a function passed to another function so that the other function can call it. 

function greet(name) {
  console.log(`Hello ${name}`);
}

function processUser(callback) {
  callback("Sanjana");
}

processUser(greet);

Here, greet is passed into processUser().

Inside processUser(): 

callback("Sanjana");

calls the function.

Important: Not All Callbacks Are Asynchronous

This is one of the easiest things to misunderstand.

A callback does not automatically mean asynchronous. 

function processUser(callback) {
  callback();
}

console.log("A");

processUser(() => {
  console.log("B");
});

console.log("C");

This prints: 

A
B
C

The callback runs immediately.

Callback describes how a function is passed. Asynchronous describes how execution is scheduled.

These are two different concepts. 

Callback
   ↓
A function passed to another function

        ≠

Asynchronous
   ↓
Execution happens separately from
the current synchronous flow

setTimeout()

setTimeout() schedules a callback to run after a specified delay. 

setTimeout(() => {
  console.log("Hello");
}, 2000);

Conceptually: 

setTimeout()
     ↓
schedule callback
     ↓
wait until delay has elapsed
     ↓
callback becomes eligible to run
     ↓
callback executes when JavaScript can process it

The delay is not an exact execution time

This is another common misconception. 

setTimeout(() => {
  console.log("Done");
}, 1000);

It is tempting to read this as:

"Run this exactly one second from now."

A better mental model is:

The callback will not run before the timer's delay has elapsed, but it may run later depending on what JavaScript is doing.

The timer is a scheduling mechanism, not a guarantee of exact execution time.

setTimeout(..., 0) does not mean "immediately" 

console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");

The output is: 

A
C
B

Even with a delay of 0, the callback is still scheduled to run later.

Zero milliseconds means "don't wait for a timer delay", not "execute right now."

Understanding exactly why this happens will make much more sense when we learn the JavaScript event loop.

Passing a function vs calling a function

This tiny difference causes a surprisingly large number of mistakes.

Suppose: 

function doSomething() {
  console.log("Hello");
}

This: 

setTimeout(doSomething, 1000);

passes the function to setTimeout().

But this: 

setTimeout(doSomething(), 1000);

calls doSomething() immediately. 

doSomething
     ↓
pass the function

doSomething()
     ↓
call the function now

If we need arguments, we can use an arrow function: 

setTimeout(() => {
  doSomething("Sanjana");
}, 1000);

setInterval()

setInterval() is similar to setTimeout(), but instead of scheduling the callback once, it repeatedly schedules it. 

setInterval(() => {
  console.log("Hello");
}, 2000);

Conceptually: 

2 seconds
    ↓
callback
    ↓
2 seconds
    ↓
callback
    ↓
2 seconds
    ↓
callback
    ↓
...

Stopping an interval

setInterval() continues running until it is cancelled. 

const intervalId = setInterval(() => {
  console.log("Hello");
}, 1000);

clearInterval(intervalId);

The same idea applies to setTimeout(): 

const timeoutId = setTimeout(() => {
  console.log("Hello");
}, 5000);

clearTimeout(timeoutId);

setInterval() does not guarantee perfect timing either

It is tempting to think: 

setInterval(doSomething, 1000);

means:

"Run doSomething() exactly every 1000 milliseconds."

That's not a safe mental model.

Just like setTimeout(), the callback can be delayed depending on what JavaScript is doing.

The Problem with Returning from an Async Callback

Another common mistake is assuming that returning from a callback returns a value from the outer function. 

function getData() {

  setTimeout(() => {
    return "data";
  }, 1000);

}

const data = getData();

It is tempting to think that data will eventually become "data".

It doesn't.

The return belongs to the callback function. It does not return from getData(). 

getData()
   ↓
setTimeout()
   ↓
callback created
   ↓
getData() finishes
   ↓
later...
   ↓
callback runs
   ↓
return belongs to callback

This is one of the reasons asynchronous results cannot simply be treated like normal synchronous return values.

This problem eventually leads us toward Promises.

Callback Hell

Callbacks become difficult when asynchronous operations depend on one another.

Imagine: 

Get user
   ↓
Get user's posts
   ↓
Get comments
   ↓
Save comments
   ↓
Send notification

If every operation expects a callback, the code can become deeply nested: 

getUser(user => {

  getPosts(user, posts => {

    getComments(posts, comments => {

      saveComments(comments, result => {

        sendNotification(result, notification => {

          console.log("Everything finished");

        });

      });

    });

  });

});

Are callbacks bad?

No.

Callbacks are useful and are still used throughout JavaScript.

The problem is not callbacks themselves. The problem is excessive nesting and dependency between asynchronous operations.

Callback hell is a problem of structure and readability, not proof that callbacks are inherently bad.

The Mental Model 

Callback
   ↓
A function passed to another function


setTimeout
   ↓
Schedule a callback to run later


setInterval
   ↓
Schedule a callback repeatedly


Callback hell
   ↓
Too many dependent callbacks
nested inside one another


Important:
Callback ≠ asynchronous


Important:
Timer delay ≠ exact execution time

What's Next?

There is still a deeper question:

If JavaScript is executing one thing at a time, how do these callbacks actually get to run later?

That's where the call stack, Web APIs, task queue, and event loop come in.

And understanding those concepts will make the behavior of setTimeout() much less mysterious.
