Classes in JavaScript

What is JavaScript actually doing when we create objects with classes?

When I first started learning classes, the syntax looked fairly straightforward: 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(`Hello ${this.name}`);
  }
}

Then: 

const user = new User("Sanjana");

user.greet();

It seemed simple.

But the more I looked at classes, the more questions appeared.

What exactly is a class? What does new actually do? And why do we need this?

There was another question that initially confused me:

What's the difference between an instance method and a static method?

So instead of starting with the syntax, let's build the mental model behind classes.

What problem are classes solving?

Suppose we want to create several users.

Without a class, we could create objects individually: 

const user1 = {
  name: "Sanjana",

  greet() {
    console.log(`Hello ${this.name}`);
  }
};

const user2 = {
  name: "Alice",

  greet() {
    console.log(`Hello ${this.name}`);
  }
};

This works.

But we're repeating the same structure.

Both objects have a name and a greet() method.

What if we wanted to create hundreds of users?

We would want a way to describe the common structure and behavior once and then create objects from it.

That's where classes come in. 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(`Hello ${this.name}`);
  }
}

Now: 

const user1 = new User("Sanjana");
const user2 = new User("Alice");

Both are instances of User. 

             User
              ↓
      defines common behavior
              ↓
       ┌──────┴──────┐
       ↓             ↓
     user1         user2

A class gives us a way to define the common structure and behavior of objects that we create.

What does new actually do?

Consider: 

const user = new User("Sanjana");

It's easy to think of new as simply meaning "call the class."

But something more is happening.

Conceptually, we can think of it like this: 

new User("Sanjana")
        ↓
create a new instance
        ↓
initialize the instance
        ↓
run the constructor

The constructor receives "Sanjana": 

constructor(name) {
  this.name = name;
}

and uses it to initialize the new object.

We can also check: 

user instanceof User;

which gives: 

true

So:

new creates an instance from the class and runs the constructor to initialize it.

What is the constructor?

The constructor is a special method: 

class User {
  constructor(name) {
    this.name = name;
  }
}

It runs when an instance is created with new. 

const user = new User("Sanjana");

The constructor receives "Sanjana" and uses it to initialize the new object. 

new User("Sanjana")
        ↓
constructor("Sanjana")
        ↓
initialize the instance

The constructor is therefore mainly about initialization.

But what is this?

This was one of the concepts I found more confusing than I expected. 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(this.name);
  }
}

When we do: 

const user = new User("Sanjana");

inside the constructor: 

this.name = name;

this refers to the newly created instance. 

new User("Sanjana")
        ↓
new object
        ↓
this → that object
        ↓
this.name = "Sanjana"

The same method can work with different objects

Now consider: 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(this.name);
  }
}

const a = new User("Sanjana");
const b = new User("Alice");

We have two objects.

When we call: 

a.greet();

this refers to a.

So: 

this.name

is: 

"Sanjana"

When we call: 

b.greet();

this refers to b.

So the same method gives: 

"Alice"

The method is the same. The object that this refers to changes. 

                 greet()
                /       \
               ↓         ↓
              a           b
              ↓           ↓
          Sanjana       Alice

This gives us a useful mental model:

In a method call, this refers to the object associated with that call.

Instance Methods

A method like: 

greet() {
  console.log(`Hello ${this.name}`);
}

is an instance method.

We call it through an instance: 

const user = new User("Sanjana");

user.greet();

Why does it belong to the instance?

Because the operation concerns a particular user.

For example: 

class BankAccount {
  constructor(balance) {
    this.balance = balance;
  }

  deposit(amount) {
    this.balance += amount;
  }
}

When we do: 

account.deposit(100);

the method needs to know:

Which account's balance should I change?

That's why it uses: 

this.balance

The operation depends on the state of a particular instance.

So:

Instance method = behavior associated with a particular object.

Static Methods

Now we get to something that initially felt confusing. 

class User {
  static describe() {
    return "A User represents a person.";
  }
}

We call it like this: 

User.describe();

We don't need: 

const user = new User();

Why?

Because describe() isn't asking about a particular user.

It's describing the concept represented by the User class.

Compare: 

user.greet();

with: 

User.describe();

The first asks:

What does this particular user do?

The second asks:

What is a User? 
Instance method
        ↓
Particular object

Static method
        ↓
Class itself

When do we actually use static methods?

This is where the distinction becomes useful. 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return `Hello ${this.name}`;
  }

  static isValidEmail(email) {
    return email.includes("@");
  }
}

We can do: 

const user = new User("Sanjana");

user.greet();

because greeting concerns a particular user.

But: 

User.isValidEmail("test@example.com");

doesn't require a User object.

The email address is already provided.

We don't need: 

user.email

to determine whether the supplied email contains "@".

So:

Use an instance method when the operation concerns a particular instance.
Use a static method when the operation belongs to the class itself and doesn't require a particular instance.

A subtle point about this and static methods

It would be tempting to say:

Static methods don't use this.

But that's not quite correct.

A static method can use this too. 

class User {
  static describe() {
    console.log(this);
  }
}

When called as: 

User.describe();

this refers to the class.

So the better distinction is: 

Instance method
        ↓
this → instance

Static method
        ↓
this → class

Can static and instance methods have the same name?

Yes. 

class User {
  greet() {
    console.log(`Hello ${this.name}`);
  }

  static greet() {
    console.log("Hello from the User class");
  }
}

Now: 

const user = new User("Sanjana");

user.greet();

calls the instance method.

While: 

User.greet();

calls the static method. 

              User
               │
        static greet()
               │
        ───────────────
               │
        User instance
               │
        instance greet()

Inheritance

Now suppose we have a User: 

class User {
  constructor(name) {
    this.name = name;
  }

  greet() {
    console.log(`Hello ${this.name}`);
  }
}

And we want an Admin.

An Admin is also a User, but it has additional behavior. 

class Admin extends User {
  deleteUser() {
    console.log("User deleted");
  }
}

Now: 

const admin = new Admin("Sanjana");

admin.greet();
admin.deleteUser();

Both work.

Why?

Because Admin extends User. 

User
 ↓
common User behavior
 ↓
Admin
 ├── inherited User behavior
 └── additional Admin behavior

So:

Inheritance lets a child class reuse behavior from a parent class while adding or changing its own behavior.

Does inheritance copy everything?

This is an easy misconception.

It's tempting to imagine: 

User
 ↓
copy everything
 ↓
Admin

But that's not the technical model.

extends establishes an inheritance relationship.

JavaScript can then find inherited behavior through that relationship.

The underlying mechanism involves JavaScript's prototype system.

I am intentionally not going into prototypes here because that's a separate concept I want to understand properly first.

For now, the useful mental model is:

Admin can use behavior inherited from User.

Method Overriding

A child class can provide its own version of a parent's method. 

class User {
  greet() {
    console.log("Hello from User");
  }
}

class Admin extends User {
  greet() {
    console.log("Hello from Admin");
  }
}

Now: 

const admin = new Admin();

admin.greet();

prints: 

Hello from Admin

The child has overridden the parent's implementation. 

User
 └── greet()
      ↓
Admin
 └── greet()
      ↓
child implementation

super

What if the child wants to use the parent's implementation too?

That's where super comes in. 

class User {
  greet() {
    console.log("Hello from User");
  }
}

class Admin extends User {
  greet() {
    super.greet();

    console.log("Hello from Admin");
  }
}

Now: 

const admin = new Admin();

admin.greet();

prints: 

Hello from User
Hello from Admin

This: 

super.greet();

means:

Call the parent's greet() implementation. 
Admin.greet()
      ↓
super.greet()
      ↓
User.greet()

super() in constructors

super is also used when the child class has its own constructor. 

class User {
  constructor(name) {
    this.name = name;
  }
}

class Admin extends User {
  constructor(name, permissions) {
    super(name);

    this.permissions = permissions;
  }
}

Here: 

super(name);

calls the parent constructor. 

new Admin("Sanjana", "all")
          ↓
Admin constructor
          ↓
super("Sanjana")
          ↓
User constructor
          ↓
name initialized
          ↓
back to Admin
          ↓
permissions initialized

Why must super() come before this?

This was another place where the syntax initially felt arbitrary.

This is wrong: 

class Admin extends User {
  constructor(name, permissions) {
    this.permissions = permissions;
    super(name);
  }
}

The child is trying to use this before the parent initialization has happened.

In a derived constructor, super() must happen before using this.

So the correct version is: 

class Admin extends User {
  constructor(name, permissions) {
    super(name);

    this.permissions = permissions;
  }
}

The useful mental model is:

The parent class needs to initialize the inherited part of the object before the child constructor starts using this.

super() vs super.method()

These look similar but do different things.

super(...) calls the parent constructor: 

super(name);

While: 

super.greet();

calls a method from the parent class. 

super(...)
    ↓
parent constructor

super.method()
    ↓
parent method

There is one question I am deliberately leaving for another article:

If JavaScript uses prototypes underneath, what is a class actually doing?

That is a different level of the JavaScript object model.

Before answering it, I want to understand this, objects, prototypes, prototype chains, and how JavaScript looks up properties and methods.

For now, classes don't need to be mysterious.

The syntax is only the surface. The useful mental model is understanding which object we're talking about, where the behavior belongs, and how parent and child relationships work.
