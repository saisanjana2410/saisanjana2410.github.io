Closures

How can a function remember something after the function that created it has finished?

Closures were one of those JavaScript concepts that initially sounded almost magical.

A function finishes running. So how can another function still access its variables?

Let's not start with the definition. Let's start with the problem.

A simple counter 

function createCounter() {
  let count = 0;

  return function () {
    count++;

    return count;
  };
}

Now: 

const counter = createCounter();

And: 

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3

The obvious question is:

Why isn't count reset to 0 every time counter() is called?

First, understand where count lives

When createCounter() runs, it creates a local binding: 

count → 0

The returned function refers to that binding.

So when the outer function finishes, JavaScript cannot simply make the environment containing count inaccessible while the returned function still needs it.

The returned function retains access to the lexical environment around where it was created.

That retained access is what we call a closure.

The relationship between execution contexts, lexical environments, and closures is explored in more detail in Execution Context .

counter() does not create count again

This is an important distinction.

We are not doing this every time: 

createCounter();

We did it once: 

const counter = createCounter();

Then we repeatedly call the returned function: 

counter();
counter();
counter();

Each call accesses the same closed-over count binding. 

count = 0
   ↓
counter()
   ↓
count = 1
   ↓
counter()
   ↓
count = 2
   ↓
counter()
   ↓
count = 3

What about counter2?

Now we can answer another interesting question. 

const counter1 = createCounter();

const counter2 = createCounter();

These counters do not share the same count.

Why?

Because createCounter() was executed twice. Each call creates its own environment. 

counter1
    ↓
Environment A
    ↓
count = 0


counter2
    ↓
Environment B
    ↓
count = 0

Now: 

counter1();
counter1();

counter2();

console.log(counter1()); // 3
console.log(counter2()); // 2

Each closure has access to its own lexical environment.

A closure isn't a copied value

It is tempting to imagine that JavaScript takes count = 0 and attaches a copy of it to the returned function.

But that mental model doesn't explain mutation very well. 

count++;

return count;

The function is accessing the binding itself, which is why changes made by one call are visible to later calls through that same closure.

So a more useful definition is:

A closure is a function together with its retained access to the lexical environment around where it was created.

Practical Example: Private State

One of the most useful applications of closures is keeping state private. 

function createCounter() {

  let count = 0;

  return {

    increment() {
      count++;
    },

    decrement() {
      count--;
    },

    getCount() {
      return count;
    }

  };
}

Now: 

const counter = createCounter();

counter.increment();
counter.increment();

console.log(counter.getCount()); // 2

But: 

console.log(counter.count);

gives: 

undefined

There is no public count property on the returned object.

The methods can access count because they were created in the lexical environment where count exists.

Data hiding using closures

This gives us a simple form of data hiding. 

function createBankAccount() {

  let balance = 0;

  return {

    deposit(amount) {
      balance += amount;
    },

    getBalance() {
      return balance;
    }

  };
}

The outside code can interact with the account through the methods: 

const account = createBankAccount();

account.deposit(100);

console.log(account.getBalance()); // 100

But outside code cannot directly manipulate the balance binding: 

account.balance = 1000000;

That assignment doesn't change the private balance used by getBalance().

The closure has created a boundary around the state.

Practical Example: Function Factory

Closures aren't only useful for counters.

We can create functions that remember configuration. 

function multiplyBy(multiplier) {

  return function (number) {

    return number * multiplier;

  };

}

const double = multiplyBy(2);

const triple = multiplyBy(3);

console.log(double(5)); // 10

console.log(triple(5)); // 15

double remembers the multiplier from the call that created it.

triple remembers a different one. 

double
  ↓
multiplier = 2


triple
  ↓
multiplier = 3

Why does this work?

Because lexical scope is based on where a function is created, not simply where it is called. 

function outer() {

  const message = "Hello";

  return function inner() {

    console.log(message);

  };

}

inner was created inside outer.

Therefore inner has lexical access to the environment containing message.

This is the same scope relationship discussed in Execution Context .

The mental model 

Function is created
        ↓
It has a lexical surrounding
        ↓
It refers to an outer binding
        ↓
The function retains access
to that environment
        ↓
Outer function can finish
        ↓
Returned function can still
use the binding
        ↓
Closure

Once you see closures this way, counters, private state, function factories, callbacks, and many other patterns stop looking like unrelated JavaScript tricks.

They're different uses of the same underlying idea: a function retaining access to the lexical environment around where it was created.
