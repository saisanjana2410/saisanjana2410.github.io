My CSS Wasn't Broken — My Browser Was Showing Me an Old Version

I changed my CSS, GitHub Pages was serving the new file, but my website still looked old. The problem turned out to be something I wasn't thinking about: browser caching.

What I Expected

I was making some changes to my blog.

I changed my homepage, created a separate blog page, changed the navigation, and updated the CSS.

Everything looked correct in my files.

But when I opened the website...

The new styling wasn't there.

At first, I assumed something was wrong with my CSS.

My Project Structure

My project structure looked like this:

my-site/ │ ├── index.html ├── style.css ├── theme.js │ ├── blog/ │ └── index.html │ └── articles/ └── ...

My homepage contained: 

<link rel="stylesheet" href="style.css">

And my blog page contained: 

<link rel="stylesheet" href="../style.css">

Those paths looked correct.

So I thought:

"Why isn't the CSS working?"

First Assumption: The CSS File Isn't Being Served

I opened the stylesheet directly in the browser: 

https://saisanjana2410.github.io/style.css

And the CSS appeared.

So the stylesheet existed.

GitHub Pages was serving it.

That ruled out one of my assumptions.

Then I Started Questioning the HTML

I checked the homepage: 

<link
  rel="stylesheet"
  href="style.css"
>

The index.html and style.css were in the same directory.

That should resolve to:

/index.html /style.css

For the blog:

/blog/index.html

the correct path was: 

<link
  rel="stylesheet"
  href="../style.css"
>

because .. means:

Go up one directory.

So the paths were correct too.

Then Something Strange Happened

I opened: 

https://saisanjana2410.github.io/?v=2

And suddenly...

The new CSS appeared.

Nothing else had changed.

The CSS file was the same.

The HTML was the same.

The server was the same.

So why did adding ?v=2 change anything?

The Missing Piece: Browser Cache

The browser doesn't necessarily download every resource from the server every time we visit a website.

It can store previously downloaded resources locally.

For example:

First visit Browser ↓ Request style.css ↓ Server ↓ CSS ↓ Browser stores it

Later:

Visit again Browser ↓ "Do I already have this?" ↓ Cached CSS

This is useful because downloading the same files repeatedly would be wasteful.

But it can create a confusing situation while developing a website.

The Problem I Ran Into

I had effectively changed: 

style.css

from version 1 to version 2.

But the browser was still using the cached version.

So from my perspective:

Server: style.css → NEW Browser: style.css → OLD

That's why the website looked wrong even though the file itself was correct.

Why Did ?v=2 Work?

This was the part I initially found confusing.

I had: 

<link
  rel="stylesheet"
  href="style.css"
>

Then I changed it to: 

<link
  rel="stylesheet"
  href="style.css?v=2"
>

The actual CSS file is still: 

style.css

But the browser now sees the resource as: 

style.css?v=2

That's a different URL.

So the browser can no longer simply use the cached resource associated with: 

style.css

It requests the new URL.

style.css ↓ old cached resource style.css?v=2 ↓ new resource request

And suddenly the new CSS appeared.

This Is Called Cache Busting

The technique is commonly called cache busting.

The basic idea is:

Change the URL when the underlying resource changes so the browser knows it should fetch a new version.

For example: 

<link
  rel="stylesheet"
  href="style.css?v=2"
>

Later: 

<link
  rel="stylesheet"
  href="style.css?v=3"
>

Or the same idea can be used with JavaScript: 

<script src="theme.js?v=2"></script>

But Does ?v=2 Mean the Server Has a Different File?

No.

These: 

style.css

and: 

style.css?v=2

still point to the same underlying file: 

style.css

The ?v=2 is a query parameter.

Query parameters can be used for many purposes. In this case, we're mainly using one to make the resource URL different.

Another Way: Hard Refresh

I also learned that I don't necessarily need to change the URL.

I can tell the browser to reload resources instead.

In Chrome on Windows: 

Ctrl + Shift + R

or: 

Ctrl + F5

This performs a stronger refresh than a normal reload.

So during development, if my page looks like it's showing an old version, one of the first things I can try is:

Hard refresh

before assuming my code is broken.

So What Actually Happened?

My debugging process eventually looked like this:

CSS doesn't appear to update ↓ Is style.css being served? ↓ YES ↓ Is the HTML pointing to the correct file? ↓ YES ↓ Is the browser showing an older version? ↓ YES ↓ Hard refresh / cache bust ↓ New CSS appears

The important part was that the CSS wasn't actually broken.

My mental model was.

What I Was Initially Thinking

CSS doesn't work ↓ Something is wrong with CSS

But a better debugging model is:

CSS doesn't appear ↓ Is the file there? ↓ Is the path correct? ↓ Is the browser requesting it? ↓ Is it getting the latest version? ↓ Is the CSS being applied?

This is much more useful because it lets me isolate the problem instead of immediately changing code.

The Mental Model I Want to Remember

When a website doesn't reflect a change I've just made, I shouldn't immediately assume:

"My code is wrong."

There are several layers involved:

My files ↓ GitHub repository ↓ GitHub Pages deployment ↓ HTTP request ↓ Browser cache ↓ CSS/JS gets applied ↓ What I see on screen

A problem can occur at any of these layers.

In my case, the files were correct and the stylesheet was being served.

The browser was simply giving me an older cached version.

What I Want to Remember

If I change CSS or JavaScript and don't see the change:

First

Check whether the file is actually being served.

Then

Check whether the HTML references the correct path.

Then

Try a hard refresh: 

Ctrl + Shift + R

And if necessary

Use cache busting: 

<link
  rel="stylesheet"
  href="style.css?v=2"
>

The important lesson isn't:

"Always add ?v=2."

It's:

The code I wrote and the code my browser is currently using are not always the same thing.
