Execution Context

What does JavaScript actually need in order to run a piece of code?

When I first learned about execution contexts, the explanation usually started with a definition: "An execution context is the environment in which JavaScript code is evaluated and executed."

Technically, that's fine. But it didn't answer the question I actually had:

Why does JavaScript need an execution context in the first place?

Let's start there.

JavaScript has to keep track of things

Imagine JavaScript encounters this code: 

const name = "Saisanjana";

function greet(person) {
  const message = "Hello " + person;
  return message;
}

const result = greet(name);

Before JavaScript can meaningfully execute this, it needs somewhere to keep track of information.

It needs to know which variables exist, which functions exist, what values those variables have, and which code is currently being executed.

The mechanism JavaScript uses to organize this information while running code is what we call an execution context.

The global context

When your JavaScript program starts, JavaScript creates a global execution context.

Think of it as the first environment in which your program begins running. 

Global Execution Context

name   → ...
greet  → ...
result → ...

The exact internal details are more complicated, but this mental model is useful: JavaScript needs an environment where the program's bindings can live.

Then something interesting happens

Our program eventually reaches: 

greet(name);

JavaScript now has a new problem.

The function has its own variables: 

function greet(person) {
  const message = "Hello " + person;
  return message;
}

Where should person live? Where should message live? And how does JavaScript remember that it is currently executing greet?

It creates another execution context for the function. 

Function Execution Context

person  → "Saisanjana"
message → ...

Now we need a stack

There can be functions calling functions calling functions. 

one()
  ↓
two()
  ↓
three()

JavaScript needs to remember where it is. That's where the call stack becomes useful.

Conceptually, every time a function is called, its execution context is placed on the stack. 

┌─────────────────┐
│ three()         │
├─────────────────┤
│ two()           │
├─────────────────┤
│ one()           │
├─────────────────┤
│ Global          │
└─────────────────┘

When three() finishes, it is removed. Then two() can continue.

This is why the call stack follows a last-in, first-out structure.

But what happens before execution?

This is where execution context connects directly to something we already know: hoisting.

JavaScript doesn't simply start at line one and blindly execute every statement.

Before execution begins, the environment has to be prepared.

This is often taught as two phases: 

1. Creation / setup
2. Execution

During setup, JavaScript establishes the bindings needed by the code.

This explains var

console.log(x);

var x = 10;

Conceptually, during setup: 

x → undefined

Then execution begins.

So when the first line runs, x already exists and has the value undefined.

And this explains let

console.log(x);

let x = 10;

JavaScript still creates the binding for x, but it doesn't initialize it to undefined.

The binding exists, but accessing it before its declaration is evaluated results in a ReferenceError.

That's the Temporal Dead Zone.

Why this matters for closures

Now we can connect execution contexts to closures. 

function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

When createCounter() runs, JavaScript creates an execution context for that call.

Inside that environment, count exists. 

count → 0

The function returns another function which refers to count.

Even after the execution of createCounter() finishes, that returned function still has access to the lexical environment containing count.

That's the foundation of a closure.

The mental model

Instead of memorizing execution context as another JavaScript definition, I find it much easier to think about it as a chain of problems JavaScript has to solve: 

JavaScript needs to run code
          ↓
It needs an environment
          ↓
Execution context
          ↓
Functions create new contexts
          ↓
The call stack tracks those contexts
          ↓
The environment must be prepared
          ↓
Creation / setup
          ↓
Code begins running
          ↓
Execution
          ↓
Lexical environments determine
where variables come from
          ↓
Closures can preserve access
to those environments

Once I started looking at execution contexts this way, hoisting and closures stopped feeling like unrelated JavaScript rules.

They started looking like different pieces of the same system.
