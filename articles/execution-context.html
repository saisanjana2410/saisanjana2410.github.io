Execution Context

What does JavaScript actually need in order to run our code?

When I first heard the term execution context, the definition sounded simple:

An execution context is the environment in which JavaScript code is evaluated and executed.

Technically, that's correct. But it doesn't answer the more interesting question:

What does JavaScript actually need to keep track of while it runs our code?

Let's build the answer from there.

JavaScript has to keep track of things

Consider this code: 

const name = "Sai";

function greet(person) {
  const message = `Hello ${person}`;
  return message;
}

const result = greet(name);

JavaScript can't simply look at this as a list of characters and start executing randomly.

While the program is running, it has to keep track of things like:

  • Which variables exist?
  • Which values do those variables have?
  • Which functions exist?
  • What code is currently running?
  • What happens when a function is called?
  • Where should JavaScript look when a variable is referenced?

An execution context is part of the machinery JavaScript uses to organize this runtime information.

The Global Execution Context

When a JavaScript program begins, a global execution context is created.

For learning purposes, we can imagine it like this: 

Global Execution Context

name   → ...
greet  → function
result → ...

This isn't meant to be a literal diagram of the engine's memory. It's a mental model for understanding that JavaScript needs an environment in which the global code can run.

Memory Creation Phase

Before JavaScript executes the statements normally, it needs to prepare the environment.

In many beginner explanations, this is called the Memory Creation Phase or Creation Phase.

A useful learning model is: 

Execution Context

1. Memory Creation Phase
          ↓
2. Execution Phase

During the memory creation phase, JavaScript establishes the bindings needed by the code.

This is one reason the behavior we call hoisting exists.

Execution Phase

After the environment has been prepared, JavaScript starts executing the code. 

const name = "Sai";

console.log(name);

Conceptually: 

Memory Creation Phase
        ↓
name binding exists

Execution Phase
        ↓
name = "Sai"

console.log(name)

The distinction is useful because it explains why some declarations appear to behave as if they exist before the line where they are written.

The details differ between var, let, const, and functions. That's why I treat Hoisting & the Temporal Dead Zone as a separate deep dive.

What happens when a function is called?

Now consider: 

function greet(person) {
  const message = `Hello ${person}`;
  return message;
}

greet("Sai");

The function declaration itself is available in the surrounding environment.

When JavaScript reaches: 

greet("Sai");

it needs an execution context for this particular function call. 

Global Execution Context
          ↓
       greet()
          ↓
Function Execution Context

Inside that function call, JavaScript needs to deal with the parameter person and the local variable message. 

person  → "Sai"
message → "Hello Sai"

If we call the function again: 

greet("Alice");
greet("Bob");

each call has its own execution context and its own parameter binding.

The Call Stack

Functions can call other functions. 

function one() {
  two();
}

function two() {
  three();
}

function three() {
  console.log("hello");
}

one();

When one() runs, it calls two(). Then two() calls three().

JavaScript needs to remember where it currently is and which function called which.

This is where the call stack comes in. 

┌─────────────────┐
│ three()         │ ← currently running
├─────────────────┤
│ two()           │
├─────────────────┤
│ one()           │
├─────────────────┤
│ Global          │
└─────────────────┘

The stack follows a Last In, First Out model.

When three() finishes, it is removed from the top. Then two() continues.

The Call Stack is not "the memory"

This distinction is worth making because these terms are often mixed together.

The call stack is primarily about keeping track of active function calls.

It isn't simply a giant box where every JavaScript variable lives.

The execution context contains runtime information, while the call stack keeps track of which contexts are currently active.

Where does JavaScript look for variables?

Consider: 

const x = 10;

function test() {
  console.log(x);
}

test();

When test() tries to resolve x, JavaScript doesn't find a local x.

It can then follow the function's lexical relationship to its outer environment and find the outer binding.

This is where lexical scope becomes important.

And that same mechanism is fundamental to closures .

Execution Context → Scope → Closures

Consider: 

function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

During the call to createCounter(), a local count binding is created.

The returned function refers to that binding.

Even after createCounter() finishes, the returned function can continue accessing the lexical environment containing count.

That is the foundation of a closure .

Once I started looking at execution context as a solution to a problem JavaScript has to solve, the surrounding concepts became easier to connect.

Hoisting, the call stack, scope, and closures stop looking like completely unrelated vocabulary. They become different pieces of the larger picture of how JavaScript executes code.
