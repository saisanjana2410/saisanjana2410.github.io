Hoisting & the Temporal Dead Zone

Stop imagining that JavaScript physically moves declarations to the top.

"JavaScript hoists variables."

That sentence is useful when you're starting out, but it creates a strange mental picture.

It sounds like JavaScript takes this: 

var x = 10;

and physically moves it to the top.

A better mental model:

JavaScript prepares bindings for a scope before it begins executing the statements in that scope.

This is part of the environment setup described in Execution Context .

Variable Hoisting with var

Consider: 

console.log(x);

var x = 10;

This prints: 

undefined

A useful mental model is that during environment setup, the var binding is created and initialized to undefined. 

Memory Creation

x → undefined


Execution

console.log(x)
       ↓
undefined

x = 10

Notice that we don't actually need to imagine JavaScript moving the source code.

The binding existed before the execution reached the declaration.

Function Hoisting

Functions behave differently from var variables. 

greet();

function greet() {
  console.log("Hello");
}

This works.

A useful mental model is that the function declaration is available during the environment setup, including its function value. 

Memory Creation

greet → function


Execution

greet()
  ↓
"Hello"

Compare that with: 

greet();

var greet = function () {
  console.log("Hello");
};

This does not behave the same way.

The var binding exists, but during setup it is initialized to undefined. 

greet → undefined

Therefore trying to call greet() before the assignment results in: 

TypeError

This is an important distinction: 

Function declaration

greet → actual function


var + function expression

greet → undefined
        ↓
later becomes a function

What about let? 

console.log(x);

let x = 10;

This produces: 

ReferenceError

The interesting part is that x is not simply nonexistent.

The binding has been established, but it hasn't been initialized yet. 

x → uninitialized

Accessing that binding before initialization is not allowed.

The Temporal Dead Zone

The period between entering the scope and reaching the let or const declaration is called the Temporal Dead Zone. 

let x = 10;

Conceptually: 

Enter scope
    ↓
x exists but is uninitialized
    ↓
──────── TDZ ────────
    ↓
let x = 10
    ↓
x becomes initialized
    ↓
normal access allowed

If we try to access x inside the TDZ, JavaScript throws a ReferenceError.

Why doesn't JavaScript just give us undefined?

Compare: 

console.log(a);

var a = 10;

with: 

console.log(b);

let b = 10;

The first prints undefined. The second throws a ReferenceError.

The difference comes from the initialization state of the binding. 

var

binding exists
      ↓
initialized to undefined
      ↓
access allowed


let / const

binding exists
      ↓
uninitialized
      ↓
TDZ
      ↓
access forbidden

A tricky example 

var name = "Sai";

{
  console.log(name);

  let name = "Sanjana";
}

You might expect the outer name to be printed.

But this throws a ReferenceError.

Why?

Because the block has its own lexical binding for name. That inner binding shadows the outer one, and the inner binding is still inside its TDZ when console.log(name) executes.

This is one reason understanding lexical scope and closures becomes useful.

So are var, let, and const all hoisted?

Yes — if by hoisting we mean that the bindings are established during the environment setup before the code is executed.

The important difference is not whether the binding exists. The important difference is what state that binding is in before the declaration is reached. 

var
    → binding is created
    → initialized to undefined
    → early access is allowed
    
    
    let
    → binding is created
    → not initialized yet
    → early access is blocked by the TDZ
    
    
    const
    → binding is created
    → not initialized yet
    → early access is blocked by the TDZ

So saying: 

var     → hoisted
    let     → not hoisted
    const   → not hoisted

is a convenient beginner shortcut, but it is misleading if we use "hoisted" to mean "the binding exists before execution reaches the declaration."

All three bindings are established before normal execution reaches their declarations. What differs is their initialization state.

The difference is initialization

Let's put them next to each other: 

             Binding exists?     Initialized?
    
    var          Yes                 Yes → undefined
    
    let          Yes                 No  → TDZ
    
    const        Yes                 No  → TDZ

This explains their different behavior.

With var: 

console.log(a);
    
    var a = 10;

the binding already exists and has been initialized to undefined, so the result is: 

undefined

With let: 

console.log(b);
    
    let b = 10;

the binding exists, but it has not been initialized yet. The access therefore happens inside the Temporal Dead Zone, resulting in: 

ReferenceError

The same basic initialization behavior applies to const: 

console.log(c);
    
    const c = 10;

Again, the binding exists but is still uninitialized, so accessing it before the declaration is evaluated produces a ReferenceError.

So what does "hoisting" really tell us?

The word hoisting by itself doesn't tell us enough to predict what will happen.

We also need to ask:

Has the binding been initialized yet, and if so, what is its initial value?

That's a much more useful question than simply asking whether something is "hoisted."

So instead of thinking: 

var is hoisted.
    let is not hoisted.

I find this mental model much more useful: 

Before execution reaches the declaration:
    
    var
      binding exists
      ↓
      initialized → undefined
    
    
    let
      binding exists
      ↓
      uninitialized
      ↓
      Temporal Dead Zone
    
    
    const
      binding exists
      ↓
      uninitialized
      ↓
      Temporal Dead Zone

Once you think about hoisting in terms of bindings and initialization, the behavior of var, let, and const becomes much easier to predict.

This is part of the larger environment setup that happens when JavaScript creates an execution context .
