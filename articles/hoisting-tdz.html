Hoisting & the Temporal Dead Zone

Stop imagining that JavaScript physically moves declarations to the top.

"JavaScript hoists variables."

That sentence is useful when you're starting out, but it creates a strange mental picture.

It sounds like JavaScript takes this: 

var x = 10;

and physically moves it to the top.

A better mental model:

JavaScript prepares bindings for a scope before it begins executing the statements in that scope.

This is part of the environment setup described in Execution Context .

Variable Hoisting with var

Consider: 

console.log(x);

var x = 10;

This prints: 

undefined

A useful mental model is that during environment setup, the var binding is created and initialized to undefined. 

Memory Creation

x → undefined


Execution

console.log(x)
       ↓
undefined

x = 10

Notice that we don't actually need to imagine JavaScript moving the source code.

The binding existed before the execution reached the declaration.

Function Hoisting

Functions behave differently from var variables. 

greet();

function greet() {
  console.log("Hello");
}

This works.

A useful mental model is that the function declaration is available during the environment setup, including its function value. 

Memory Creation

greet → function


Execution

greet()
  ↓
"Hello"

Compare that with: 

greet();

var greet = function () {
  console.log("Hello");
};

This does not behave the same way.

The var binding exists, but during setup it is initialized to undefined. 

greet → undefined

Therefore trying to call greet() before the assignment results in: 

TypeError

This is an important distinction: 

Function declaration

greet → actual function


var + function expression

greet → undefined
        ↓
later becomes a function

What about let? 

console.log(x);

let x = 10;

This produces: 

ReferenceError

The interesting part is that x is not simply nonexistent.

The binding has been established, but it hasn't been initialized yet. 

x → uninitialized

Accessing that binding before initialization is not allowed.

The Temporal Dead Zone

The period between entering the scope and reaching the let or const declaration is called the Temporal Dead Zone. 

let x = 10;

Conceptually: 

Enter scope
    ↓
x exists but is uninitialized
    ↓
──────── TDZ ────────
    ↓
let x = 10
    ↓
x becomes initialized
    ↓
normal access allowed

If we try to access x inside the TDZ, JavaScript throws a ReferenceError.

Why doesn't JavaScript just give us undefined?

Compare: 

console.log(a);

var a = 10;

with: 

console.log(b);

let b = 10;

The first prints undefined. The second throws a ReferenceError.

The difference comes from the initialization state of the binding. 

var

binding exists
      ↓
initialized to undefined
      ↓
access allowed


let / const

binding exists
      ↓
uninitialized
      ↓
TDZ
      ↓
access forbidden

A tricky example 

var name = "Sai";

{
  console.log(name);

  let name = "Sanjana";
}

You might expect the outer name to be printed.

But this throws a ReferenceError.

Why?

Because the block has its own lexical binding for name. That inner binding shadows the outer one, and the inner binding is still inside its TDZ when console.log(name) executes.

This is one reason understanding lexical scope and closures becomes useful.

So are let and const hoisted?

This question causes a lot of confusion because the word "hoisting" is used informally.

If by hoisting we mean:

"The binding is established before execution reaches the declaration."

then it is reasonable to say that let and const are hoisted.

But if we mean: 

"I can access the variable before its declaration."

then no.

That's why this simplified rule is misleading: 

var     → hoisted
let     → not hoisted
const   → not hoisted

A more useful model is: 

var
→ binding exists
→ initialized to undefined
→ early access gives undefined


let
→ binding exists
→ uninitialized
→ TDZ
→ early access gives ReferenceError


const
→ binding exists
→ uninitialized
→ TDZ
→ early access gives ReferenceError
→ must be initialized in declaration

The bigger picture

Hoisting isn't really a story about moving source code. It is a useful shorthand for understanding what happens when JavaScript prepares an execution environment.

That preparation is part of the larger model described in Execution Context .

And once we understand that bindings belong to lexical environments, we have the foundation for understanding closures .
